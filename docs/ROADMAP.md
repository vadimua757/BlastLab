# BlastLab Sandbox — Roadmap (TASK 002–011)

Статус: TASK 001 завершено (`72a03f0`). Наступний TASK починається лише після підтвердження власника.

## Концепція
Мобільний полігон: гравець будує конструкції з блоків, розміщує вигадані «заряди» (Blast Orb) з абстрактними параметрами (рівень 1–5, радіус в ігрових одиницях, візуальний стиль), запускає їх і спостерігає руйнування — уламки, VFX, сповільнення часу. Мішені — лише блоки та предмети.

### TASK 002 — Scene flow і головне меню
- **Мета:** MainMenu → кнопка «Play» → Sandbox → «Back» → MainMenu.
- **Що зробити:**
  - `ISceneLoader` в Application і `SceneLoader` (async `SceneManager.LoadSceneAsync`) у Core.
  - `GameStateMachine` при зміні стану запускає завантаження сцени.
  - UI меню на uGUI: Canvas, Safe Area для вирізів екрана.
  - Тимчасовий bootstrap, якщо Sandbox запущено в Editor напряму (щоб тестувати сцену окремо).
- **Тести:** EditMode — стейт-машина викликає `ISceneLoader` (fake). PlayMode — перехід MainMenu → Sandbox → MainMenu.
- **Готово, коли:** перехід працює в Editor і в APK; Android-кнопка «Назад» повертає в меню.

### TASK 003 — Камера і тач-керування
- **Мета:** орбітальна камера над полігоном.
- **Що зробити:**
  - Input System: 1 палець — обертання, 2 пальці — переміщення, pinch — масштаб; у Editor — миша.
  - `CameraRigController` (Presentation); межі, швидкості та інерція — у `CameraSettings` (ScriptableObject).
  - Логіка обмежень (clamp кутів і дистанції) — чистий C# в Application.
- **Тести:** EditMode на clamp та інерцію.
- **Готово, коли:** камера не заходить під підлогу чи за межі полігону; плавна в APK.

### TASK 004 — Доменна модель і каталог об'єктів
- **Мета:** описати, що можна ставити на полігон, без прив'язки до Unity.
- **Що зробити:**
  - Domain: `ObjectId`, `ObjectCategory` (блок, проп, заряд), `DurabilityTier` (абстрактні рівні 1–5), `SandboxLayout` (розміщені об'єкти: позиція, поворот).
  - Core/Presentation: `ObjectDefinition` (ScriptableObject: id, prefab, іконка, категорія, рівень міцності) і `ObjectCatalog`.
  - Правила розміщення (сітка, межі, ліміт об'єктів) — у Domain.
- **Тести:** EditMode на правила розміщення та унікальність id у каталозі.
- **Готово, коли:** каталог з 5–8 базовими блоками та 1 зарядом створюється й валідується.

### TASK 005 — Система розміщення
- **Мета:** ставити, вибирати, рухати, обертати й видаляти об'єкти.
- **Що зробити:**
  - Панель каталогу (скрол з іконками).
  - Raycast по тапу, прив'язка до сітки, прев'ю-«привид» перед встановленням.
  - Command pattern в Application: `PlaceObject`, `MoveObject`, `DeleteObject`; стек Undo/Redo.
  - Режими «Будівництво» / «Запуск» (підстани `GameStateMachine` або окрема стейт-машина Sandbox).
- **Тести:** EditMode на Undo/Redo та заборону накладання об'єктів.
- **Готово, коли:** можна зібрати вежу з 20 блоків, скасувати 5 кроків і повторити їх.

### TASK 006 — Руйнівні конструкції
- **Мета:** блоки ламаються на уламки.
- **Що зробити:**
  - Заздалегідь розбиті (pre-fractured) варіанти префабів; runtime-розбиття на мобільних занадто дороге.
  - `Integrity` — абстрактне «здоров'я» блока, залежить від `DurabilityTier`; при 0 ціла модель замінюється уламками з пулу.
  - Конструкції кінематичні, доки їх не зачепить ефект (економія фізики).
- **Тести:** EditMode на втрату цілісності; PlayMode — блок з нульовою цілісністю дає уламки з пулу, а не нові об'єкти.
- **Готово, коли:** блок, зруйнований з коду, розпадається; після 10 циклів GC.Alloc у профайлері не росте.

### TASK 007 — Абстрактний ефект заряду
- **Мета:** заряд впливає на блоки в радіусі.
- **Що зробити:**
  - `BlastDefinition` (ScriptableObject): рівень сили 1–5, радіус (ігрові одиниці), `AnimationCurve` спаду, множники візуалу.
  - Simulation: чистий C# `BlastResolver` — позиція заряду + цілі → «шкода цілісності» та «ігровий імпульс» для кожної цілі. Обидва значення — налаштовувані криві, не фізичні формули.
  - Presentation застосовує `AddForce` і передає шкоду в `Integrity`.
  - Пошук цілей — `Physics.OverlapSphereNonAlloc`, без алокацій.
  - Ланцюгова реакція: заряд у радіусі іншого спрацьовує із затримкою.
- **Межі безпеки:** жодних реальних матеріалів, TNT-еквівалентів, тиску чи радіусів ураження. Параметри — суто ігрові, описані в AGENTS.md.
- **Тести:** EditMode на детермінованість `BlastResolver`, монотонний спад, ланцюгову реакцію.
- **Готово, коли:** заряд руйнує вежу; налаштування змінюються лише в ScriptableObject.

### TASK 008 — VFX, аудіо і пулінг
- **Мета:** виразний відгук без втрат продуктивності.
- **Що зробити:**
  - Генеричний `ObjectPool<T>` в Infrastructure на основі `UnityEngine.Pool`.
  - Пули для уламків, частинок і звуків; ліміт активних уламків, найстаріші плавно зникають.
  - Стилізовані URP-частинки (спалах, пил, хвиля), тряска камери, haptics на Android.
  - `VfxSettings` і `AudioSettings` (ScriptableObject) з бюджетами під рівні якості.
- **Тести:** EditMode на пул (повернення, ліміт, переповнення).
- **Готово, коли:** 5 зарядів підряд без помилок і GC-спайків; бюджети задокументовані.

### TASK 009 — Керування часом і перезапуск
- **Мета:** сповільнення, пауза, «Reset» до стану перед запуском.
- **Що зробити:**
  - `TimeController` в Application поверх `ITimeSource`: 1x / 0.25x / пауза, `fixedDeltaTime` коригується синхронно.
  - Snapshot розміщення перед запуском і відновлення одним тапом.
  - Опційно: камера слідує за найбільшою групою уламків.
- **Тести:** EditMode на масштаб часу та відновлення зі snapshot.
- **Готово, коли:** цикл «будую → запускаю → повертаю → змінюю» займає < 2 секунд дій гравця.

### TASK 010 — Збереження і налаштування
- **Мета:** кілька збережених сцен і налаштування гравця.
- **Що зробити:**
  - Infrastructure: `JsonLayoutRepository` у `Application.persistentDataPath`; версія схеми з міграцією; атомарний запис (тимчасовий файл → заміна).
  - Слоти збережень з мініатюрою (скріншот).
  - Налаштування: якість, звук, вібрація, чутливість камери.
- **Тести:** EditMode — збереження/читання, міграція старої версії, пошкоджений файл.
- **Готово, коли:** після перезапуску APK сцена відновлюється.

### TASK 011 — Оптимізація і реліз
- **Мета:** стабільна робота на реальних пристроях.
- **Що зробити:**
  - Профілювання на 2–3 Android-пристроях (слабкий, середній, флагман): Profiler, Frame Debugger, Memory Profiler.
  - Рівні якості Low / Medium / High з автовибором; LOD, batching, ліміти фізики (solver iterations, кількість rigidbody).
  - Release: keystore поза репозиторієм, AAB для Google Play, IL2CPP, stripping.
  - CI (GitHub Actions): EditMode-тести та Android-збірка; Unity-ліцензія — у GitHub Secrets.
- **Готово, коли:** цільовий FPS визначено за результатами профілювання (не наперед); release-збірка проходить у CI.

## Наскрізні правила
- **Архітектура:** Domain → Application / Simulation → Presentation; Infrastructure підключається через Core. Нові asmdef — лише з поясненням.
- **Тести:** кожен TASK додає EditMode-тести на логіку; PlayMode — з TASK 002.
- **Продуктивність:** без `FindObjectOfType` і LINQ у гарячих циклах; NonAlloc-запити фізики; пули.
- **Безпека:** лише абстрактні ігрові параметри; перевірка в кожному TASK, що зачіпає Simulation.
- **Процес:** один TASK — один коміт/PR, звіт за форматом AGENTS.md, підтвердження перед наступним.
